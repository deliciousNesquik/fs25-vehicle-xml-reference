# Farming Simulator 2025
## Элемент `<parentFile>`

```xml
<parentFile xmlFilename="$data/vehicles/brand/model/model.xml">
    <attributes>
        <set    path="vehicle.storeData.price" value="21000"/>
        <remove path="vehicle.wheels.wheelConfigurations.wheelConfiguration(1)"/>
        <clearList path="vehicle.designConfigurations.designConfiguration" keepIndex="1"/>
    </attributes>
</parentFile>
```

Наследование XML: файл берёт **родительский XML за основу** и накладывает на него правки
(`set`/`remove`/`clearList`). Это **общий механизм движка** (работает в любом XML: техника,
placeable, сейв, modDesc), а не фича именно `modDesc`. В `modDesc` встречается редко — основное
применение это наследование конфигов техники.

> Расположение: корень любого XML движка (в т.ч. дочерний `<modDesc>`). Раздел справочника — modDesc.

---

## 1. Что это

`<parentFile>` объявляет другой XML как базу и патчит его. При загрузке движок **заменяет** текущий
файл дескриптором родителя с применёнными правками. Важное следствие: из дочернего файла берётся
**только блок `<parentFile>`**, все прочие его элементы **игнорируются** — итог = родитель + правки.

Механизм встроен в загрузчик XML и срабатывает прозрачно для любого XML, который открывает движок.

---

## 2. Атрибут `xmlFilename`

| Атрибут | Тип | Описание |
|---|---|---|
| `xmlFilename` | STRING[^string] | Путь к родительскому XML — основе. |

Как резолвится путь:

- **Относительный** — от каталога текущего мода (родительский XML лежит **внутри этого мода**).
- **`$data/...`** — файл базовой игры (например `$data/vehicles/brand/model/model.xml`).
- Ссылка на файл **другого установленного мода** нативно не работает (нужен community-мод Extended
  Filenames). Родитель — либо в своём моде, либо в данных игры.

---

## 3. Операции в `<attributes>`

Необязательный блок `<attributes>` содержит правки (в любом количестве и сочетании):

| Операция | Атрибуты | Действие |
|---|---|---|
| `<set>` | `path`, `value` | Установить/создать значение по XML-пути[^xpath] в родителе (пишется строкой). |
| `<remove>` | `path` | Удалить узел/атрибут по пути из родителя. |
| `<clearList>` | `path`, `keepIndex` | Очистить повторяющийся список по пути, оставив один элемент (какой — задаёт `keepIndex`). |

Синтаксис `path` — стандартный XML-путь движка: элементы через `.`, индекс повторяющегося элемента
`(n)`, атрибут через `#attr`. Пример: `vehicle.storeData.price` или `...wheelConfiguration(1)`.

---

## 4. Как применяется

При загрузке файла движок:

1. Грузит родителя (`xmlFilename`).
2. Применяет правки: сначала все `remove`, затем все `set`, затем все `clearList` (по группам, а не
   в порядке записи).
3. Отбрасывает дочерний дескриптор и работает дальше с родителем + правками.

Если родитель не загрузился — в лог пишется предупреждение `Failed to load parent xml file '...'`,
и наследование не применяется.

---

## 5. Где реально используется

- **Конфиги техники и placeable** — основной кейс. Мод-вариант (реколор, аддон, изменённая
  комплектация) ссылается `<parentFile xmlFilename="$data/vehicles/.../model.xml">` и меняет пару
  узлов (цена, конфигурации, стор-категория). При этом `storeItem` указывает на **дочерний** XML.
- **В `modDesc`** — редко. Осмысленно, когда мод содержит несколько почти одинаковых
  `modDesc`-вариантов, наследующих один шаблонный `modDesc` внутри того же мода, и меняющих через
  `set` только часть (например заголовок или версию).

---

## 6. Ограничения

- Родитель **не** объявляется как `<dependency>`; он должен физически резолвиться при загрузке
  (внутри мода или `$data`).
- Ссылка на файл другого мода нативно не поддерживается.
- Собственные элементы дочернего файла (кроме `<parentFile>`) в результат не попадают — всё, что
  нужно изменить, задаётся через `set`/`remove`/`clearList`.

---

## 7. Пример (наследование техники)

```xml
<!-- дочерний vehicle.xml мода -->
<vehicle>
    <parentFile xmlFilename="$data/vehicles/brand/model/model.xml">
        <attributes>
            <set    path="vehicle.storeData.price"        value="18500"/>
            <set    path="vehicle.storeData.brand#name"   value="MYBRAND"/>
            <remove path="vehicle.designConfigurations"/>
        </attributes>
    </parentFile>
</vehicle>
```

---

## 8. Типичные ошибки

- **Ожидание, что прочие элементы ребёнка «домержатся»** — нет, читается только `<parentFile>`,
  остальное игнорируется.
- **Ссылка на файл другого мода** — нативно не резолвится.
- **Путаница с `<dependencies>`** — `parentFile` не требует установки отдельного мода; родитель
  берётся из своего мода или из данных игры.
- **Неверный `path`** — путь должен соответствовать структуре родительского XML.

---

## 9. Примечания

- `<parentFile>` — общий механизм наследования XML движка, не привязан к `modDesc`; для техники он
  особенно полезен (варианты одной базовой машины без копирования всего XML).
- Итоговый файл = родитель + правки; дочерний файл несёт только `<parentFile>`.
- Механика подтверждена по загрузчику XML FS22 (движок общий с FS25; открытого зеркала загрузчика
  FS25 нет). Точную индексацию `keepIndex` стоит проверить на своей сборке.
